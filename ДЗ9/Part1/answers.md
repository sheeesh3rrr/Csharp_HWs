## Задача 1.1

### 1. Почему `ProcessDamage` принимает `List<IDamageable>`, а не `List<Player>` или `List<Trap`?

Метод ProcessDamage принимает List<IDamageable>, потому что интерфейс позволяет работать с разными объектами, которые умеют получать урон. Например, это могут быть игрок и ловушка. Если использовать List<Player>, то метод сможет работать только с игроками, а если List<Trap> — только с ловушками. Благодаря полиморфизму мы можем вызывать один и тот же метод TakeDamage() у разных объектов, при этом каждый объект будет выполнять его по-своему. Это делает код более универсальным и удобным для расширения.

### 2. Нарушает ли `Trap` контракт `IDamageable`?

Само по себе возвращение false может быть допустимым, если по договорённости метода это означает, что объект уничтожен или больше не может продолжать существование. Но реализация Trap не уменьшает HP, а свойство HP всегда возвращает 10 и игнорирует запись. Поэтому вызывающий код, который ожидает, что TakeDamage действительно изменяет состояние объекта, столкнётся с неожиданным поведением. Контракт интерфейса должен описывать не только сигнатуру метода, но и ожидаемый смысл его работы; здесь поведение ловушки как минимум неоднозначно и требует уточнения контракта.

### 3. Что будет, если пытаться лечить `HealthPotion` через `ProcessDamage`?

HealthPotion реализует интерфейс IHealable, потому что его назначение — лечить объекты, а не получать урон. Если попытаться передать зелье в ProcessDamage, программа выдаст ошибку компиляции, потому что этот метод принимает только объекты типа IDamageable. Зелье не реализует этот интерфейс и не имеет обязательного для него метода TakeDamage. Поэтому для лечения в GameSystem предусмотрен отдельный метод ProcessHeal, который принимает список IHealable и вызывает Heal().

### 4. Что произойдёт при добавлении `IsDead` в `IDamageable`?

Если в интерфейс IDamageable добавить свойство IsDead, то изменить придётся классы Player и Trap, потому что оба реализуют этот интерфейс. В каждом классе необходимо будет добавить реализацию нового свойства. Например, у игрока IsDead может возвращать true, если HP меньше или равно нулю. У ловушки можно использовать отдельное состояние, которое показывает, разбита она или нет. Если не добавить это свойство, программа выдаст ошибку компиляции, потому что классы не будут полностью реализовывать интерфейс.


## Задача 1.2. 

| Утверждение | Abstract class | Interface |
|---|:---:|:---:|
| Может содержать поля с конкретными значениями | + | - |
| Может иметь полноценный конструктор | + | - |
| Один класс может наследовать/реализовывать несколько таких типов | - | + |
| Может содержать реализацию метода по умолчанию | + | + |
| Может объявлять свойства без реализации | + | + |
| Может быть использован как тип поля или переменной | + | + |
| Может наследовать классы | + | - |
| Может содержать приватные методы | + | + |

### Комментарии 

1. **Поля с конкретными значениями.** Абстрактный класс может хранить поля и значения в них. Интерфейс не может содержать обычные поля экземпляра.

2. **Конструктор.** Абстрактный класс может иметь конструктор, который вызывается при создании объекта дочернего класса. Интерфейс не имеет конструктора.

3. **Несколько типов.** Класс может наследовать только один класс, но может реализовывать несколько интерфейсов одновременно.

4. **Реализация метода по умолчанию.** Абстрактный класс может содержать обычные методы с готовой реализацией. В современных версиях C# интерфейсы тоже могут содержать методы с реализацией по умолчанию.

5. **Свойства без реализации.** И абстрактный класс, и интерфейс могут объявлять свойства без готовой реализации, которую должен предоставить класс.

6. **Тип поля или переменной.** И абстрактный класс, и интерфейс можно использовать в качестве типа переменной или поля. Это позволяет хранить ссылки на объекты соответствующих классов.

7. **Наследование классов.** Абстрактный класс может наследоваться от другого класса. Интерфейс не может наследовать класс, но может наследовать другие интерфейсы.

8. **Приватные методы.** Абстрактный класс может содержать приватные методы. В современных версиях C# интерфейсы тоже могут содержать приватные методы для внутренней логики.


## Дополнительный вопрос 

Я бы создала абстрактный класс Character, от которого будут наследоваться Player, Enemy и NPC. В абстрактном классе можно разместить общие для всех персонажей свойства и методы, например Name, HP и TakeDamage(), потому что все три сущности могут получать урон.

Для взаимодействия с игроком я бы создал интерфейс IInteractable с методом Interact(). Его будут реализовывать только классы Player и NPC, так как только они могут взаимодействовать с игроком и открывать диалоги. Для восстановления здоровья я бы создал интерфейс IHealable с методом Heal(), который будет реализовывать только Player.

              Character (abstract)
              /        |        \
          Player     Enemy      NPC
            |                    |
      IInteractable         IInteractable
      IHealable

Таким образом, абстрактный класс подходит для хранения общих характеристик и поведения всех персонажей. Интерфейсы позволяют добавлять отдельные возможности только тем классам, которым они действительно нужны. Если в будущем появится новый персонаж, ему можно будет добавить нужные интерфейсы без изменения общей структуры классов.
